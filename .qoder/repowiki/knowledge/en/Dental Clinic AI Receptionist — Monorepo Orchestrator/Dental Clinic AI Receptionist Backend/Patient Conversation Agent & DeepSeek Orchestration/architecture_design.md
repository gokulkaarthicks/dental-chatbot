Two cooperating sub-packages form the agent layer:

- `app/agent/` is the orchestration surface. `runner.py` implements the single-turn entry point `run_turn`, which loads conversation history, builds system/provider messages via `prompts.py`, invokes the provider through `DeepSeekClient.chat`, executes any requested tool calls via `tools.execute_tool`, persists assistant/tool turns, merges and deduplicates interactive cards, formats prose via `reply_format.py`, and returns a `TurnResult`. A bounded loop (`MAX_TOOL_ROUNDS=4`, `MAX_TOOL_CALLS_PER_ROUND=4`) prevents runaway model round-trips; special handling exists for re-asks of availability, DSML-native tool markup, family-option clicks injected by the UI, and emergency handoff notices.
- Tool definitions are split into two registries: `tools.py` holds identity/registration/practice-info tools (with Pydantic argument models and a frozen `ToolSpec` registry), while `scheduling_tools.py` adds Phase 3 scheduling tools (availability search, proposals, confirmations, reschedules, cancellations, family booking, emergencies, staff requests). The combined registry is resolved lazily in `_all_specs()` to break the circular import between the two files. Every handler receives a `ToolContext` dataclass carrying the authenticated session/patient/conversation — never trust model arguments for identity.
- `app/ai/deepseek.py` is a minimal OpenAI-compatible HTTP client over `httpx` against DeepSeek's `/chat/completions`. It defines typed exceptions (`DeepSeekError` subclasses with user-facing messages), exponential-backoff retries for 429/5xx/network errors, strict timeouts, and a DSML parser that extracts function invocations embedded in raw text when the provider does not populate `tool_calls`.

Dependency direction inside the module: runner → (deepseek client + tools registry) → services layer (`app.services.*`). The runner owns state persistence and flow control; tools delegate business logic to services and return structured dicts whose `cards` field drives the UI.
